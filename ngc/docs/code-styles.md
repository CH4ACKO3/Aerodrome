# 零号工程 00.13：同一实验的三种代码写法

这一节只改变代码组织，不改变物理、算法或默认参数：一维质点从静止出发，用比例反馈达到 2 m/s。加速度限幅 ±1 m/s²，控制周期 0.02 s，共 250 步。状态包含位置和速度；输入在每步内保持，调用框架的精确常加速度积分。

从 `ngc/` 执行：

```sh
uv run --locked python projects/code_styles/script_style.py
uv run --locked python projects/code_styles/functional_style.py
uv run --locked python projects/code_styles/object_style.py
```

三种入口均支持 `--output PATH`，默认分别写入 `artifacts/styles/script`、`functional`、`object`，包含 `summary.json` 和 `trajectory.npz`。代码只需核心依赖，不需要绘图或训练库。

| 写法 | 读代码的顺序 | 状态放在哪里 | 适合什么 |
|---|---|---|---|
| 脚本式 | 参数→循环→输出，从上到下 | 脚本变量 | 第一次理解算法、一次性实验 |
| 函数式 | 明确参数→计算函数→结果 | 函数局部变量，结果显式返回 | 参数扫描、算法复用、数值测试 |
| 面向对象式 | 创建→reset→step/run | 对象实例 | 交互运行、分段推进、多个独立环境 |

## 先理解相同的数学

反馈为 `a=clip(K(v_target-v), -a_max, a_max)`。一步物理更新为 `p_next=p+v*dt+a*dt²/2`、`v_next=v+a*dt`。加速度是实际输入，不会在物理函数里偷偷再次限幅。

未饱和时误差满足 `e_next=(1-K*dt)e`；有加速度限幅时，初始阶段先近似线性增加速度。三份程序都依赖 `aerodrome.models.point_mass.step`，没有复制三套积分器。

## 脚本式：最容易读，复用时要留意副作用

`script_style.py` 的参数和执行顺序全部在顶层，适合边读边运行。导入这个文件也会解析命令行并运行实验，因此把它当可执行脚本使用，不作为库导入。这是本节有意保留的对比，不是推荐整个项目都这样写。

## 函数式：输入输出明确

`functional_style.py` 的 `simulate()` 不写文件、不打印、不依赖上一轮结果。给同样参数就得到同样轨迹；换目标速度时直接传 `target_m_s`。文件操作只在 `main()` 中。该函数式组织仍使用普通 Python 循环，并不自动等于 JAX 编译；编译与批量执行是另外一个维度。

练习：导入 `simulate`，分别传入目标速度 −2、0、2，并叠加结果。不要先复制三份函数。

## 面向对象式：管理明确的状态生命周期

`object_style.py` 的实例保存参数和当前物理状态。调用 `step()` 会修改该实例；再次调用 `run()` 会接着运行，而不是自动重置。需要新的一轮时明确调用 `reset()`。两个对象拥有独立状态。

这里没有抽象基类、继承层次或工厂。仅当对象确实拥有状态、资源或生命周期时，才值得引入对象；不需要把每一个加法都包装成一个类。对象内部仍可调用纯函数。

练习：先推进 100 步，再推进 150 步，比较一次推进 250 步的末状态；随后 reset，确认新的实验重新从指定初态开始。分段 `run()` 的时间轴是相对本次调用的时间，拼接记录时需要加上已有时长并去掉重复边界点。

## 如何选择

写公式验证的小实验可以从脚本开始；出现参数扫描和复用需求时抽出函数；需要交互环境或分段执行时增加一个管理状态的对象。实战工程常用“纯数值函数 + 薄的运行入口”，而不是在三种风格中选一种后强制所有文件遵循它。

三种写法的轨迹应一致，额外用解析离散误差检查数值正确性。不能只证明三个程序同样写错。端到端测试实际运行三个命令并读取它们保存的数据。
